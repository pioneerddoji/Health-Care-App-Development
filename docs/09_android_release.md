# 9. 안드로이드(Google Play) 출시 준비 — 종합 체크리스트

> 2026-07-12 기준. `docs/06_deployment.md`(양 플랫폼 공통 가이드)의 안드로이드 심화판.
> 아래 순서대로 진행하면 된다. ⛔ = 출시 차단(반드시 해결), ⚠️ = 심사 리스크.

## 0. 현재 상태 요약

| 영역 | 상태 |
|---|---|
| 앱 기능 (로드맵 0~7단계 + 피드백 1~3차) | ✅ 완료, 회귀 테스트 통과 |
| 빌드 준비물 (eas.json, 아이콘/스플래시, app.json) | ✅ 준비됨 (번들 ID만 자리표시) |
| Supabase 스키마/RLS/Edge Function 코드 | ✅ 준비됨 (**실환경 미검증**) |
| 개인정보처리방침/이용약관 | ✅ 초안 (**법률 검토 전**) |
| SMS 문자 인증 | ✅ 1차 출시는 우회(off 기본값 — 이메일 확인만). 실발송(live)은 v1.1 |
| 결제(Play Billing) | ⛔ 미연동 (페이월 UI만 존재) |

## 1. 출시 전 반드시 결정할 것 (사용자 결정 사항)

1. **⛔ 번들 ID(패키지명) 확정** — 현재 `app.kidcare.mvp`는 자리표시.
   소유 도메인 역순 권장(예: `kr.co.도메인.kidcare`). **Play 첫 업로드 후 영구 변경 불가.**
2. **✅ 1차 출시의 구독 정책 — 결정됨 (2026-07-12)**: 무료 플랜만 개방 +
   **얼리버드 가격**(무료 기간 가입자는 유료 플랜 월 ₩1,000 할인, 정가
   ₩3,900/₩5,900에 취소선 표기). 실서버 빌드 기본값이 페이월 `hidden` 모드라
   그대로 빌드하면 됨. 상세: docs/07 §가격 전략.
   - ⚠️ 과금 시작(v1.1) 시 필수: 비얼리버드 신규에게 정가 실제 부과(표시광고법),
     할인 유지 기간 결정(권장: 구독 유지하는 한 계속).
3. **✅ 회원가입 문자 인증 처리 — B안 구현 완료 (2026-07-17)**:
   `EXPO_PUBLIC_SMS_MODE` 플래그(demo/off/live) 신설, **실서버 빌드 기본값 off**
   (문자 인증 건너뜀 — 이메일 확인만으로 가입, 비밀번호는 재설정 메일로 대체).
   그대로 빌드하면 1차 출시 요건 충족.
   - ⚠️ 추후 A안(live) 전환 시: SMS 공급자 계약 + **OTP 생성·검증의 서버(Edge
     Function) 이전 필수** — 현재 smsAuth.ts의 검증은 앱 내 데모 구현이라
     그대로 live로 켜면 안 된다(우회 가능/레이트리밋 없음).
   - ⚠️ off 모드 운영 준비물: Supabase Confirm email 켜기 + 비밀번호 재설정
     링크 도착지(Site URL 또는 재설정 웹 페이지) 설정.
4. 앱 이름 최종 확정("아이케어" — Play 내 중복/상표 검색 권장), 아이콘 시안 확정 여부.

## 2. 계정·인프라 준비 (사용자 직접, 코드로 대신 불가)

### 2-1. Google Play 개발자 계정
- [ ] 등록($25 일회성) + 본인 확인(신분증/D-U-N-S). **개인 계정보다 조직(사업자) 계정 권장**:
  - 개인 계정(2023-11 이후 신규)은 **프로덕션 출시 전 비공개 테스트 의무**
    (일정 수의 테스터가 14일 연속 참여 — 인원 요건은 정책 변동이 있으니 콘솔 안내 확인).
    조직 계정은 이 요건이 없다.
  - 구독 과금 계획이 있으므로 어차피 사업자·통신판매업 신고가 필요해짐.
- [ ] 결제 프로필 연결(수익 발생 대비), 개발자 페이지 정보 입력.

### 2-2. Supabase 운영 프로젝트 (약 30분, `docs/06_deployment.md` B-1 그대로)
- [ ] ⛔ 프로젝트 생성 — **서울 리전(ap-northeast-2)** 권장. 국외 리전이면
  개인정보처리방침에 국외 이전 항목 구체화 필요.
- [ ] schema.sql → schema_stage3.sql → schema_subscriptions.sql → schema_settings.sql 순서 실행.
- [ ] Edge Function 배포(`share-report`, `--no-verify-jwt`).
- [ ] `npm run verify:supabase` **전부 PASS** 확인 → 실기기에서 supabase 모드 스모크.
- [ ] 운영 설정: Confirm email 켜기 + 커스텀 SMTP, PITR 백업(Pro 플랜) 검토.

### 2-3. 개인정보처리방침·약관 (법률)
- [ ] ⛔ `docs/privacy_policy.html`을 실 도메인에 호스팅(GitHub Pages/Vercel 가능)
  — Play 등록 폼에 URL 필수.
- [ ] ⛔ **법률 검토**: 아동 건강정보(민감정보) + 만14세 미만 법정대리인 동의 구조는
  일반 템플릿보다 엄격하게 본다. 이용약관(`src/constants/terms.ts`)도 함께.
- [ ] ⛔ **계정 삭제 웹 페이지**: Play 정책상 계정 생성이 있는 앱은 "앱 밖(웹)에서도
  삭제를 요청할 수 있는 URL"을 데이터 보안 폼에 제출해야 한다. 앱 내 삭제는 이미
  구현돼 있으므로, 삭제 안내+요청 접수 페이지 하나만 호스팅하면 됨(정적 페이지 가능
  — 요청 시 제작해 두겠음).
- [ ] 구독 과금 시작 시점에: 통신판매업 신고, 환불 정책 고지.

## 3. 남은 개발 작업 (내가 처리 — 결정만 내려주면 됨)

- [ ] ⛔ 번들 ID 반영(`app.json`) — §1-1 결정 후 즉시.
- [x] §1-2 대비 구조: 결제 추상화(`billing.ts`)·웹훅(`billing-webhook`)·페이월 3모드
  플래그 완료 — A안은 기본값 그대로, B안은 docs/07 §실연동 절차(SDK 계약 후 반나절).
- [x] §1-3 반영 완료: 문자 인증 우회 플래그(`EXPO_PUBLIC_SMS_MODE`, 기본 off) +
      비밀번호 재설정 메일 대체 경로. (공급자 연동은 v1.1 — OTP 서버 이전 포함)
- [ ] 사진 서명 URL 24h 만료 시 재발급 로직(장시간 사용 대비 — 출시 전 권장).
- [ ] 버전 표기(`app.json` version/versionCode) 정리 + 릴리즈 노트 초안.
- [ ] (선택) Sentry 등 크래시 리포팅 — 베타 피드백 수집에 유용.

## 4. 빌드 → 테스트 트랙 (반나절)

- [ ] `eas login` → `eas init` → EAS Secrets에 운영 env 등록(06 문서 B-3 명령 그대로).
- [ ] **내부 테스트**: `eas build --profile preview --platform android`(APK)
  → 내부 테스터에게 바로 배포하거나, `eas submit`으로 내부 테스트 트랙 업로드.
- [ ] **실기기 확인 목록(안드로이드 특화)**:
  가입(OTP)→동의→아이 등록(달력 픽커)→기록(시계 픽커/사진 첨부·권한 팝업)→
  기록 상세 팝업/사진 뷰어 스와이프→대시보드 드래그 순서 변경→PDF 생성(2배 폰트
  확인)·공유 시트→공유 링크(수신 브라우저 열람→회수 차단)→접종 알림
  (**Android 13+ 알림 권한 팝업** 확인)→보호자 초대(두 기기)→동의 철회→데이터 삭제→
  구독 게이팅(🔒 칩)→재시작 후 데이터/그래프 순서 유지.
- [ ] 프로덕션 AAB: `eas build --profile production --platform android`
  (서명 키는 EAS 관리 + Play App Signing 사용 — 키 분실 걱정 없음).
- [ ] 비공개 테스트 트랙(베타): 지인 테스터 이메일/그룹 등록 → 피드백 수집.

## 5. 스토어 등록 정보 + 심사 폼 (Play Console)

- [ ] 스토어 리스팅: 앱 이름/짧은 설명(80자)/자세한 설명, 스크린샷(폰 최소 2장,
  실기기 캡처), 그래픽 이미지(1024×500). 카테고리: **"건강/운동" 또는 "라이프스타일"**
  (의료 카테고리 회피 — 심사 기준 상승).
- [ ] **데이터 보안(Data safety) 폼**: 건강 정보 수집=예(앱 기능 목적, 전송 중 암호화,
  삭제 요청 가능), 사진, 이메일/전화번호. 계정 삭제 URL 입력(§2-3).
- [ ] ⚠️ **건강 앱 선언(Health apps declaration)**: 건강 데이터를 다루는 앱은 별도
  선언 폼 제출 — "보호자의 관찰 기록 도구, 진단·처방 기능 없음"으로 답변.
  우리 불변 원칙(의료행위 금지)이 그대로 심사 방어 논리가 된다.
- [ ] ⚠️ **대상 연령/아동 정책**: 대상 그룹 = **성인(보호자)**. 아동이 사용하는 앱이
  아님을 명확히(아동 대상으로 표시하면 Families 정책이 적용돼 훨씬 엄격해짐).
  스토어 문구에도 "보호자용" 표현 유지.
- [ ] 콘텐츠 등급 설문(IARC) — 전체이용가 예상.
- [ ] 광고 없음 신고, 뉴스 앱 아님, 정부 앱 아님 등 선언 항목.
- [ ] 심사 노트: 데모 계정(`demo@kidcare.app`) 또는 심사용 테스트 계정 제공.

## 6. 출시 이후 운영

- [ ] 단계적 출시(예: 20%→100%) 활용, ANR/크래시 대시보드(Play Vitals) 모니터링.
- [ ] JS만 고치는 수정은 `eas update`(OTA)로 심사 없이 배포 가능
  (네이티브 모듈 추가 시에는 새 빌드+심사).
- [ ] RLS 테스트 CI 깨진 채 배포 금지(기존 원칙), anon key는 공개 전제·RLS가 방어선.
- [ ] Supabase 무료 플랜은 1주 미사용 시 일시정지 — 운영은 Pro 권장.

## 순서 요약 (크리티컬 패스)

```
결정 3건(§1: 번들ID·구독·SMS)
  → 개발 반영(§3) + Play 계정/Supabase/방침 호스팅(§2, 병행)
  → 내부 테스트 빌드 + 실기기 확인(§4)
  → 비공개 테스트(베타) 피드백 1~2주
  → 스토어 리스팅/폼 작성(§5) → 프로덕션 AAB 제출 → 심사(보통 수일)
```
가장 오래 걸리는 항목은 보통 **계정 본인확인, 법률 검토, (개인 계정일 경우)
비공개 테스트 의무 기간**이므로 §2를 가장 먼저 시작하는 것이 좋다.
