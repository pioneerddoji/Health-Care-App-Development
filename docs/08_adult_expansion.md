# 8. 향후 확장 설계 노트 — 성인(가족 전체) 건강 관리

> 2026-07-12 사용자 요청: "향후 성인 관리로 확대하는 것을 고려해서 설계에 반영".
> 지금 당장 기능을 만들지는 않되, **확장을 막는 결정을 하지 않는 것**이 이 문서의 목적.

## 현재 구조가 이미 수용하는 것
- `children` 테이블/타입은 `birth_date` 기반이라 나이 상한이 스키마에 없다
  (0–18세 제한은 UI 문구·검증 계층에만 존재). 성인 레코드도 저장 자체는 가능.
- 기록 12종·건강관리 영역 14종은 연령 중립적 개념이 대부분(수면/식사/복용/증상 등).
- Repo 패턴 덕분에 "대상자(care recipient)" 개념 확장은 인터페이스 한 곳에서 시작.

## 확장 시 갈라지는 지점 (지금부터 지키는 규칙)
1. **개념 명명**: 새 코드·문서에서는 "아이"가 본질이 아닌 로직(기록/그래프/레포트/공유)에
   `child`를 새로 하드코딩하지 않는다. 기존 명칭 일괄 변경(`children` → `care_recipients`)은
   마이그레이션 비용이 크므로 **백로그** — 확장 결정 시점에 view/alias로 점진 전환.
2. **동의 모델 분기**: 만 14세 미만=법정대리인 동의(현행), 14세 이상~미성년=본인+법정대리인,
   **성인=본인 동의 필수**(타인이 성인의 건강정보를 대신 기록하려면 성인 본인의 위임 동의
   흐름이 별도로 필요). `consents` 테이블은 대상자 단위 행이므로 `consent_type` 컬럼
   추가로 수용 가능 — 스키마 재설계 불필요.
3. **연령 전제 로직 격리**: 성장 백분위(소아 전용), 예방접종 일정(연령표),
   등원/등교 기록 유형처럼 연령 전제가 있는 기능은 이미 독립 모듈이라
   "대상자 유형별 노출" 스위치만 붙이면 된다.
4. **구독 한도 명명**: `maxChildren`은 의미상 "등록 대상자 수" — 확장 시
   `ENTITLEMENTS` 한 파일만 고치면 되는 구조 유지(현행 원칙 그대로).
5. **불변 원칙 승계**: 의료행위 금지(진단/용량/내원 판단 금지)는 성인 대상에도 동일 적용.

## 확장 착수 시 순서 (예상)
① 대상자 유형 필드(`recipient_type: child|adult`) 추가 → ② 성인 본인 계정-대상자 연결
(본인 기록 모드) → ③ 동의 흐름 분기 → ④ 연령 전제 기능 노출 스위치 → ⑤ 명칭 정리.
